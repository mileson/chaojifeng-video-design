# 源码说明片：从产品源码和选题侧重点做出说明类宣传片

目录：适用与入口 · 总流程 · 源码调研 · 事实账本 · 侧重点映射 · 口径边界 · 取证 · 叙事与章节 · 开场钩子 · 旁白、字幕与时间 · 声音 · 验收与登记 · 实战要点 · 与其他方法的关系

配方 `product-source-explainer`，名称“源码说明片”，别名“源码驱动产品宣传”“产品源码说明片”。所属场景 `product-promo`，视觉语法沿用[极简左右讲解](../templates/product-split-explainer.md)，工作单见[源码说明片模板](../templates/product-source-explainer.md)；成片案例见 README 的[产品宣传片](../README.md#产品宣传片)。

这是产品宣传的第三种入口：用户给的是**产品本体**和**想强调的价值**，由 Agent 自己从源码里找事实、取证据、定叙事，做成一条让目标用户看懂“这个产品替我做什么”的说明片。参考素材入口给的是片子，模板名称入口给的是版式，本入口给的是产品和重点。

## 适用与入口

| 用户提供 | 缺失时怎么办 |
| --- | --- |
| 产品源码目录 | 必须有。目录含多个子项目时，按侧重点选相关入口；仍无法判断再问 |
| 选题侧重点 | 几句话或几个关键词都行，顺序就是优先级。没给时，从产品自述和近期版本里挑 2 到 3 项最能被画面证明的价值，写明选择理由 |
| 参考片或风格 | 可选。没有就用极简左右讲解的视觉语法 |
| 声音、画幅、时长 | 可选。画幅默认 9:16（1080×1920）；本人音色只在用户明确指定本人讲解时使用 |

源码用来**确认事实与限制**，不是镜头来源；镜头来自产品真实运行的结果。侧重点是**约束**，不是目录：章节、时长和证据都向侧重点倾斜，其余能力最多一句话带过，不做功能清单。

## 总流程

| 阶段 | 产物 | 要点 |
| --- | --- | --- |
| 1 调研 | 产品档案 | 读说明、版本、用户可见文案、限制与测试，记 `path:line` |
| 2 账本 | `ledger.json` | 事实、来源、侧重点、口径边界、证据、章节、主张互相对得上，`product_ledger.py check` 通过 |
| 3 映射 | 侧重点到章节 | 每个侧重点一章，用户措辞换成产品对外措辞 |
| 4 取证 | 真实界面与产出 | 按证据阶梯取当前版本的运行结果，脱敏，不触发真实副作用 |
| 5 叙事 | 故事线、分镜卡 | 先写开场钩子与揭晓，再串章节；章节写成“前态 → 操作 → 结果” |
| 6 文案 | 旁白稿 | 先读 `chaojifeng-creator-style`；每句主张对应账本里的事实 |
| 7 声音 | 配音、词级时间戳、乐床 | 整稿一次合成；字幕、镜头、闪避都从同一份排程派生 |
| 8 制作 | 成片与可编辑工程 | 按[制作流程](production-workflow.md)渲染，一次只跑一个重任务 |
| 9 验收 | 检查记录、交付登记 | 逐章回答验收问题，设计、预览、导出、听审、观众理解分别登记 |

用户已说明不需要确认，或要求 direct 时，全程连续完成，在最终回复里交代选择与缺口；候选叙事线自己选并写理由，不停下等。

```sh
python3 SKILL_ROOT/scripts/product_ledger.py init /path/to/product-source --out /project/video/ledger.json
python3 SKILL_ROOT/scripts/product_ledger.py check /project/video/ledger.json --source /path/to/product-source --evidence-root /project/video --script /project/video/narration.txt
```

## 源码调研

按下面顺序读，读到足以支撑侧重点就停，不通读全库。`init` 会把版本出处、文档、视觉资产和限制线索列成候选，只是起点，每一条仍要打开原文核对。

1. **对外口径最权威的文案**：商店说明、官网文案、README 的用户部分、发布说明。它们告诉你产品怎么对用户说话。
2. **版本与形态**：清单、包配置、工程文件，得到对外名称、版本、平台和权限。目录名与产品名不同时两个都记，口播用界面和商店上的名称。
3. **用户看得见的入口**：路由、页面、菜单、本地化文案、新手引导。用户实际读到的词比代码标识可靠。
4. **限制与权益**：配额、会员、开关默认值、发布策略配置。它们决定哪些话能说、哪些要收窄。
5. **测试与夹具**：测试证明行为，夹具常能直接拿来取证。
6. **现成视觉资产**：商店截图、图标、设计稿、教程图；先核对版本与当前界面是否一致。

README、商店文案与代码冲突时，以当前磁盘的代码和实际运行为准，在账本里记一条冲突，不顺手采信数字更大的那个。不运行来路不明的脚本，不用线上正式账号。

## 事实账本

账本是内部文件。[`templates/product-ledger.json`](../templates/product-ledger.json) 给出每个部分的写法，`scripts/product_ledger.py` 负责生成骨架和检查闭合。

| 部分 | 记什么 |
| --- | --- |
| `product` | 对外名称、版本及出处、平台、目标用户、一句话定位及出处、源码根与调研日期 |
| `emphasis` | 用户原话、对外说法、观众所得、支撑事实、对应章节；状态 `supported` 完全成立、`narrowed` 收窄后成立、`unsupported` 不成立 |
| `facts` | 一条事实一句陈述，带 `path:line`、版本、状态 `verified／unknown`、是否可对外 |
| `boundaries` | 不对外说或要收窄的事：类别、原因、出处，以及可扫描的禁用词 |
| `evidence` | 每张截图或录屏怎么取、哪个版本、哪天、层级、支撑哪些事实、是否脱敏 |
| `chapters` / `claims` | 章节用哪些证据；口播主张引用哪些事实 |
| `framings`（可选） | 开场里替观众说话的句子：痛点 `pain`、顾虑 `worry`、疑问 `question`；不是产品主张，不引用事实，但要写明由哪条边界收住（顾虑必填） |

规则：

- 只有 `verified` 且可对外的事实能进入口播和字幕。`unknown` 先去核实，核实不了就删主张。
- 替观众说话的句子（“是不是又费时又费力”）不是产品主张，登记进 `framings`，不要为了让它“有依据”把它塞进 `claims`；它们照样受边界禁用词扫描。
- 数字、配额、价格、平台数这类易变的值，只用当前版本核到的；进片时写成不绑定日期的说法，或在账本里写明核对日期。侧重点不涉及时就不进片。
- 每条口播主张至少有一份证据在画面上支撑同一件事；证据与主张讲的不是同一件事，等于没有证据。

`check` 只检查账本是否闭合、来源是否真的存在、禁用词有没有出现在稿件里，不能判断事实对不对，也不替代真实运行取证。

## 侧重点映射

把用户的每个侧重点拆成：用户原话 → 对外说法 → 观众所得 → 支撑事实 → 章节。

- 用户措辞与产品措辞不同时（例如用户说“多账号运营”，界面里叫“发布空间”），口播用产品的词，并在首次出现时用一句话把两者接上：观众既认得自己的需求，也认得界面上的字。
- 侧重点与产品不符时三选一：收窄口径并写原因；换成最接近的真实能力；标 `unsupported` 并在交付说明里告知。不为迎合用词编造能力。
- 章节数 2 到 5。时长按用户给的顺序和证据厚度分配，不平均；用户没给顺序时，把最容易一眼看懂的放前面。
- 侧重点之外的能力可以在尾幕前用一句话带过，不独立成章。

## 口径边界

先问：这句话谁来负责？产品默认怎么做？哪些是会员或保留功能？哪些写进片里会被误解？

- 把“不对外说”或“必须收窄才能说”的事写进 `boundaries`，类别如会员权益、保留未公开、未核实、平台条款与默认行为、授权与隐私。每条给出处与可扫描的禁用词。
- 边界不一定是缺点。产品默认由用户确认后才发布，是产品行为，也是卖点；写进片里用受众的话讲，不写成制作说明。
- 个人信息、账号、密钥、内部地址不出现在任何画面、文件名或字幕里。

## 取证

取证的真实性比好看重要。按阶梯取，能用上一层就不用下一层。

| 层级 | 证据 | 进成片 |
| --- | --- | --- |
| 1 | 当前版本真实运行后的截图或录屏 | 首选 |
| 2 | 官方商店或官网素材，已核对版本与当前界面一致 | 可用，登记来源与核对结果 |
| 3 | 受控夹具驱动真实界面：用源码自带的预览或测试夹具，让真实页面渲染业务数据 | 可用，登记夹具与数据来源 |
| 4 | 按组件状态重建 | 只作内部预览，进成片前必须与 1 到 3 对照 |
| 5 | 凭空绘制不存在的界面或功能 | 禁止 |

取不到的证据，降低主张，不用重建冒充。

| 产品形态 | 取证路线 |
| --- | --- |
| iOS／macOS App | `xcodebuild` 到指定 `-derivedDataPath`，再 `xcrun simctl boot／install／launch／addmedia`，用 `simctl io booted screenshot` 截图；只启动一个模拟器，用产品自带的示例素材 |
| 浏览器扩展 | Playwright 管理的 Chromium，持久上下文加 `--disable-extensions-except` 与 `--load-extension`（新版品牌 Chrome 已不接受命令行加载，不用它）；或用源码自带的预览入口在普通浏览器里渲染页面，路由只放行本机，细节见[真实界面成片工程](real-ui-film-engineering.md) |
| Web 应用 | 本地起开发服务，用 Playwright 截图或录屏 |
| 桌面应用 | 构建并运行，截取窗口 |
| 命令行与 SDK | 真实命令与真实输出，还原成终端面板 |
| 微信小程序 | 使用 `weapp-dev-mcp` |

取证规则：

1. **按成片画幅取证。** 竖版要局部放大：用 2 倍像素密度，先决定每个镜头要裁哪一块，再定视口；不要先截整屏再硬裁。
2. **只有静态标签不够。** 每章至少一段“前态 → 操作 → 结果”的连续证据（局部放大、高亮、前后态），而不是标签加静态图轮播。
3. **不触发真实副作用。** 发布、支付、发送、删除、登录一律不在取证里发生；用只读状态、夹具数据或脱敏后的状态。
4. **先脱敏再入库。** 头像、昵称、邮箱、令牌、会话、地址栏、本机路径；脱敏后的文件才进入成片素材目录，原图不进。
5. 每份证据在账本 `evidence` 里登记怎么取、哪个版本、哪天、支撑哪些事实。

## 叙事与章节

沿[产品宣传视频](product-promo-direction.md)先写首尾再串主体。默认顺序是：**观众的麻烦与疑问 → 解决方案 → 怎么操作 → 收束**。这是用户 2026-11-05 看完“结果先行”的第二版之后提出的：产品类讲解通常先问“你是不是遇到过这样的情况”，引起共鸣，再给解决方案，再讲怎么操作；开篇要有让观众产生疑问的钩子。

- **开场钩子**：先替观众把麻烦和顾虑说出来，最后收成一个疑问。写法见下一节。
- **揭晓**：疑问之后一句话给出答案：产品名、形态，再用一句“这几件事，它都能做”回收钩子里的期待；画面把疑问逐个翻成对勾。
- **结果**：揭晓后马上放一个最有画面感的结果，作为答案的第一个证明，回答“我会得到什么”（例如“点一下，五个平台的发布页都填好了”）。
- **章节**：一章一个侧重点，写成“前态 → 操作 → 结果”，口播讲价值，画面证明。版式和证据变奏按[极简左右讲解](../templates/product-split-explainer.md)。
- **尾幕**：回到揭晓时的产品名与成果，一句自然的品牌句；品牌句要有账本里的事实撑着，不夸大。
- 候选叙事线 1 到 3 条（痛点钩子、结果先行、产品定位开场），写清各自的观众所得与风险，选一条并记理由。痛点钩子是默认；用户明确要结果先行，或产品没有观众一听就点头的麻烦时才换，并写明理由。结果先行仍然成立：首幕独立构图，先把最有画面感的结果放出来，再引出产品。

## 开场钩子

**用户已确认的方向**（2026-11-05）：开篇要有吸引人的钩子，一开始先让观众有疑问；先讲观众遇到的情况引起共鸣，再给解决方案，然后告诉观众怎么操作。他给的场景是：一份内容发多个平台费时费力，还担心用 AI 会被限流封号；想找一款能多账号、一键发到多个平台、还能帮忙搬运的；从 X、公众号、飞书之间互相搬内容的痛点。下面的结构、时长和口径规则，是在“一键发”这一次实战里整理出来的做法，没有经过观众验证，换产品时按产品调整。

| 句 | 作用 | 写法 | 一键发的实例 |
| --- | --- | --- | --- |
| 1 痛点 | 最普遍、最容易点头的麻烦 | 用提问说出费时费力的那件事 | 一份内容要发好几个平台，是不是又费时又费力？ |
| 2 顾虑 | 观众已有的替代办法和担心 | 观众的口吻，不替产品辩护 | 想用 AI 代发，又怕被限流封号。 |
| 3 痛点 | 第二个侧重点的麻烦 | 点出具体场景和笨办法 | 公众号、飞书、X 之间搬文章，全靠复制粘贴。 |
| 4 疑问 | 把痛点收成期待 | 按章节顺序列出，句末是问号 | 有没有一款，一键发多个平台，还能搬运，账号也分开管？ |
| 揭晓 | 给出答案，回收期待 | 产品名、形态，再一句概括 | 这就是一键发，装在 Chrome 里的扩展，这几件事，它都能做。 |

做法：

1. **句数与时长。** 痛点、顾虑、疑问共 3 到 4 句，一句一个画面，每句 2 到 4 秒；钩子约 14 秒，加揭晓约 18 秒；首句在 0.3 秒内开口。太长观众没等到产品就划走，太短又不够共鸣；这是一次实测的起点，没有完播数据，看了数据再调。
2. **句句是观众的话，不是产品主张。** 钩子句不引用事实，但登记进账本的 `framings`，写明类型（`pain`、`worry`、`question`）和由哪条边界收住。`check` 只验结构与边界禁用词，不验痛点是否真实；痛点来自用户给的场景或目标观众的真实麻烦，不编数据和情节。
3. **顾虑最容易越界。** 观众担心限流、封号、审核、AI 时，产品往往不能承诺它的反面。顾虑只当观众的话说一次，不演示“规避”；片中任何位置不说“不会限流”“不封号”“更安全”，对应边界写进 `boundaries` 并带上可扫描的禁用词。后文只讲产品真实的默认行为（例如默认由用户逐个检查后自己点发布），也不拿它当安全承诺。观众的替代办法（例如“用 AI 代发”）只是替代办法，不等于产品有这项能力。
4. **期待与章节一一对应。** 疑问句里的期待按章节顺序排，揭晓之后的章节顺序、片尾清单与之一致；被收窄的侧重点，期待句用收窄后的说法（多账号写成“账号也分开管”，不写“同时发多个账号”）。
5. **揭晓句挂在开场章节。** “这几件事，它都能做”概括的是后面几章，在账本里作为开场章节的一条主张，引用各侧重点的事实；证据用后面各章的证据，列进开场章节的 `evidence_ids`。`check` 要求主张的每个事实都有本章证据，这一步不能省。
6. **画面。** 钩子用独立构图，一句一幕，不放真实界面；平台名与图标用产品自带资源。画面动作演示“为什么麻烦”（一站一站地填、复制粘贴来回搬、盖上“限流”“封号”章），不用空洞的动效填时间。真实界面从揭晓之后进入。
7. **句式。** 钩子仍先读 `chaojifeng-creator-style`。创作风格对设问、反问的限制与用户明确要求的疑问钩子冲突时，以用户要求为准，但不连续堆叠反问，不堆三句以上同结构的排比。

声音与配乐见 [讲解配音的声音方向](narration-voice-direction.md#开场钩子的声音与配乐)；画面与时间映射见 [真实界面成片工程](real-ui-film-engineering.md#开场前置后的时间映射)。

## 旁白、字幕与时间

- 文案先读 `chaojifeng-creator-style`。口吻像了解产品的人在讲：定位 → 各章价值 → 场景或成果 → 品牌句。无依据的效果、数据、评价和个人经历不写。
- **得到一条连续音频和词级时间戳。** 本机 Qwen3-TTS 路线整稿一次合成，不把分句音频按字节拼接；云端克隆路线按意思完整的段落分段合成、每段多取样择优，再按字级时间戳与能量边缘拼成一条连续旁白并重建词级排程，做法见 [讲解配音的声音方向](narration-voice-direction.md)。
- **单一排程**：字幕（HTML 与 SRT）、镜头切点和乐床闪避都从同一份词级排程派生。排程检查：时间单调、每条时长为正、不重叠、字幕文字完整覆盖旁白。
- 字幕展示层去掉独立短句的句末标点，保留一份 `source_text` 做覆盖校验；配音稿保留自然停顿所需的标点。
- 时长随旁白，不强塞。两到四章的说明片通常 60 到 100 秒，以完整表达和实际音频为准。

## 声音

- 旁白声音按 [讲解配音的声音方向](narration-voice-direction.md)：超级峰自己的产品和内容，默认用他已授权的本人声音（云端克隆音色，或本机参考音色，见 [Qwen 配音接入](qwen3-tts-narration.md)），语速偏快、有起伏；替他人制作或授权不明时才用通用声，并写明它偏平、偏慢。云端克隆音色是收费路线，先说明服务、费用和预算上限，口播文字会发给服务商，不新建音色。
- 乐床：用户指定 > 项目已选 > 已核实使用范围的素材；人声期间闪避，尾句后保留完整尾音再淡出。没有可核实的音乐时，用无乐床或本地生成的方案，并写明缺口。
- 回听（ASR）只能判断读错、漏字、加字，不能判断自然度和像不像；没有人耳听过就写 `not_checked`。

## 验收与登记

逐章回答：

1. 这一章对应的侧重点是否清楚？观众看完能不能复述它？
2. 口播的每个主张，画面上有没有同一件事的证据？
3. 证据来自哪一层？有没有重建冒充？
4. 有没有触碰口径边界？有没有个人信息出现在画面、字幕或文件名里？
5. 缩到 360×640，主操作和结果还看得清吗？字幕有没有挡住界面？
6. 开场钩子：前三秒目标观众能不能认出自己的麻烦？顾虑句有没有被说成产品承诺？疑问句里的期待与章节、片尾清单顺序一致吗？揭晓句挂的证据在后面各章吗？

技术检查：首帧、前三秒、各章中点、尾帧；全片文字扫描（制作身份标签、禁用词、独立短句末尾标点）；字幕与音频对齐；ASR 回听；响度与峰值；成片里确实同时有人声和乐床；`product_ledger.py check` 通过；`validate_plan.py` 与 `check_delivery.py` 通过。

登记设计、预览、导出与实测、听审、观众理解五项，各自如实写 `not_run／partial／passed／not_checked`。账本、工作单和取证原图留在内部目录，不作为观众附件交付；对外文字、文件名和音轨直接采用受众表达，不加制作身份标签。

## 实战要点

首次完整制作（浏览器扩展“一键发”，2026-11-05）留下的做法，换产品时同样适用：

- **用户措辞与产品词的接法。** 用户说“多账号运营”，产品里叫“发布空间”（对应 Chrome 个人资料）。标题沿用用户的说法，旁白第一句先用白话说“同一个平台有好几个账号，也能分开管”，再引入产品的词；同时在边界里写明产品没有一次同发多个账号的能力，状态标 `narrowed`。
- **开场画面与额度要对得上。** 开场展示的平台数超过普通用户的每日额度时，不报数字，用旁白一句话加尾幕小字收窄为“有限、会员更多”；能不冲突就让开场不超过额度。边界的禁用词要避开自己的对外文字，例如禁了“3 个平台”，副标题就不能写这个数。
- **自述与上架口径不一致就记一条边界。** 说明文档写着“仅供个人学习自用、不要商用”，商店却已上架并收费时，账本记 `license` 边界，片中不出现“开源”“自用”之类的词，交付时提醒用户自行核对授权。商店版本落后源码一版时，画面取源码当前版本，片中不放版本号，账本里记差异。
- **依赖额外工具或授权的功能收窄说。** 搬到飞书需要额外安装命令行并授权时，只说“第一次用要先连接飞书”，不说“一键连接”“零配置”。
- **引导图和商店图逐张查个人信息。** 产品自带的引导图里可能带着作者的公开昵称或邮箱，使用前看清，必要时避开；商店快照存档时去掉开发者邮箱。
- **计划与交付登记用脚本从排程生成。** 排程变了重跑脚本，计划哈希、素材哈希和交付里的产物哈希一起更新，旧检查不继承给新成片。
- **声音反馈来得晚，设计要能整体重做。** 第一版用通用声做完，用户听了说“音色单调、语速慢”。第二版换成本人声音，整体语速从 3.72 提到 5.84 字/秒，口播起止点全部移动；时间只有一个来源，画面按口播起止点做分段线性时间映射，字幕、音效、计划和交付登记跟着重新生成，分镜不用重写。方法见 [讲解配音的声音方向](narration-voice-direction.md) 与 [真实界面成片工程](real-ui-film-engineering.md#旁白重做后的时间映射)。
- **开场改成钩子，后面不必重做。** 第三版（用户要求开篇钩子）只新增钩子四句和揭晓句共 5 段口播，把原来开场的两句并入其中；三章与片尾的口播文字、取样、取证和画面都不动。设计时间线在最前面加一段，成片排程按节拍拼好后，用同一套分段线性映射对齐，两份排程的节拍 id 与分句数必须一一对应，见 [真实界面成片工程](real-ui-film-engineering.md#开场前置后的时间映射)。需要重做的只有：新增口播的配音、开场画面、开场乐床与音效、字幕、计划、交付登记和账本的开场部分。
- **钩子里的顾虑要单独过一遍边界。** 开场提到“想用 AI 代发，又怕被限流封号”时，账本把它登记成 `worry`，由“不承诺发布成功与账号安全”“不讲 AI 接入”两条边界收住；后面的章节没有出现反面承诺，字幕、画面文字与文件名也扫过禁用词。顾虑是观众的话，不是产品的优点，这一点在交付说明里也要说清。
- **钩子的时长要算进整体，钩子段的语速要单独量。** 钩子加揭晓使片长从 63 秒增到 75 秒，整体语速从 5.84 降到 5.62 字/秒（含停顿），有声段从 6.70 降到 6.53。钩子加揭晓的有声段只有约 6.0 字/秒，比正文的 6.7 慢：句间留白、提问语调和“公众号、飞书、X”这类枚举都占时间。用户一贯要求快，钩子偏慢是否可接受要听了再定；要更紧时，先给钩子段加语速重抽取样，不要靠删掉句间的“问、停、答”压时长。
- **三项检查逐步放行。** 账本闭合、计划严格校验、交付探测依次通过；没有整片连续播放和人耳试听时，视觉、播放、听感写 `partial`，观众理解写 `not_run`，交付状态为 `partial` 是准确结果。
